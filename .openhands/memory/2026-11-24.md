# 2026-11-24 — the confirmed-only alert mode

## The ask

The owner said it in one line: "خليك تخبرني بس بالإشعارات المهمة والمؤكدة"
(only important + confirmed alerts). He then sent two setups as the MODEL of
what "confirmed" means to him:

- 🟢 Buy (counter-trend, needs proof): "condition = 15m candle **closes above**
  3572.43 (exits the bearish FVG); entry 3573.50, stop 3565.50, target
  3585.92 then 3594.44; R:R 1.6 / 2.6."
- 🔴 Sell (with trend): "condition = 15m candle **closes below** 3552.67 with
  **volume > 3000**; entry 3551.50, stop 3560.50, target 3514.55; R:R 4.1."

The common shape: a CONDITION (a 15m close past a level, sometimes with a
volume threshold), then entry/stop/target/R:R. Not "price is near a level".

## What was built

- ⭐ **`confirm_watch(seen)` + `_confirm_msg()` in bot.py.** One new watch, gated
  by `CONFIRM_ONLY` (`DESK_CONFIRM_ONLY`, default OFF, panel key
  `confirm_only`). It reads only CLOSED bars on `CONFIRM_TF` (15m) and speaks
  when a close lands past a live/sticky level by more than `CONFIRM_EPS_PTS`
  (3.0, == `SUPPORT_BREAK_PTS` so the two alerts agree on "broken").
- ⭐ **It is a SPEAKING mode, not a filter.** It never changes what the desk
  trades; it changes what the desk says. Deliberately kept out of `GATE_KEYS`
  so `open_all`/`close_all` cannot silently flip the owner's alert volume —
  there is a test pinning exactly that (`test_the_mode_is_off_by_default`).
- ⭐ **In confirm mode, three watches are not CALLED at all**, not merely muted:
  `entry_watch` (an APPROACH: "price near a sell zone" — fires before anything
  happened, the clearest example of what he does not want), `levels_watch` (an
  INTRABAR pierce that can recover), and `support_watch` (its 15m-close break is
  the same evidence `confirm_watch` now carries, so it would double-speak).
  `gate_watch`, `trend_watch`, `news_*` and `trade_watch` stay: they are already
  bar-close/structural facts with their own cooldowns. Tests assert calls AND
  non-calls, because a watch that runs and returns None still burns a tape read.
- **The volume verdict** (`_vol_verdict`): the closing bar's `tickVolume` vs the
  **median** of the previous `CONFIRM_VOL_LOOKBACK` (20) bars on the same frame.
  ≥ `CONFIRM_VOL_MULT` (1.0) = "الحجم: مؤكّد", below = "الحجم: ضعيف … ممكن يكون
  فخ". Median not mean: one news spike drags a mean far enough that every later
  bar reads "thin" and the verdict becomes a constant. Gold's real 15m
  `tickVolume` sits ~2.5-6k with a ~3.9k median, so the owner's "volume > 3000"
  and a 1.0× median are the same order — but the multiple, not the absolute
  3000, is what survives a regime change.
- The card also carries the **air pocket** (distance to the next fresh level in
  the break's direction, claimed only when ≥10 pts) and the **divergence** line
  from `_divergence_note()` — the ONE producer the map also reads.
- Sizing comes from `_sized()`, the same function the desk trades on, so the
  card cannot quote a trade the engine would refuse. ⚠ This means our stop is
  the engine's 12-point/$12 window, NOT the 8-point stop in the owner's buy
  example. Say this out loud rather than hardcoding his numbers: a card that
  quotes one price while the engine executes another is two contradicting cards.
- `_target_ladder()` supplies the runner rungs when levels allow ("ثم: …").

## Traps hit (worth keeping)

- ⚠ **`closed()` drops the newest bar**, so a 2-bar test feed tests the
  `len(b) < 3` guard instead of the rule. The test feed pads to 25 bars at the
  front; a short feed silently returns None and looks like a logic bug.
- ⚠ **`unittest.mock.patch.object(...)` stores a `_patch`, not the mock.** The
  handle is what `p.start()` RETURNS. A helper that returns the `_patch` fails
  with `'_patch' object has no attribute 'assert_called'`.
- ⚠ **A helper that patches a name and a test that patches it again**: the
  inner patch wins and the outer mock sees nothing. The helper must hand its own
  handles back to the test; do not re-patch in the test.
- ⚠ A re-cross of a level is a NEW confirmed event and must SPEAK (it
  invalidates the call just given) — my first test asserted silence there and
  the code was right. Do not "fix" the code to match a wrong expectation.
- The sticky pool's keys are `lvls` / `zones` / `liq` / `touches` — NOT
  `levels`. Reading the wrong key yields an empty set and the watch goes silent
  with no error (`with suppress(Exception)` around it hides it entirely).

## ⚠️ Render `PUT /env-vars` REPLACES the whole list — it does NOT merge

- Cost: one `PUT` with only the two keys I wanted (`DESK_CONFIRM_ONLY`,
  `DESK_ALERTS`) **wiped `TG_TOKEN`, `DESK_SYMBOL` and the four gate vars** off
  the live service. The API answers 200 with exactly the keys you sent, so the
  response *looks* like success.
- The live container kept running (the token was already in memory), so
  `/health` stayed green and hid it: **the damage is only visible on the next
  restart**, when `app.py` prints "no token" and exits 2. A green `/health`
  after an env change proves NOTHING about the env.
- `GET /env-vars` returns the values for everything EXCEPT secrets
  (`TG_TOKEN` came back as a real value here, but a `sync: false` var is
  write-only — assume you cannot read back what you must not lose).
- ⭐ **Rule: read the full list, append, send the WHOLE list back.** Never PUT a
  partial array to change one key.
- Also: `PUT /env-vars` does NOT trigger a redeploy by itself; the push did.
- To add one var safely, either send all keys, or use
  `PATCH`-per-key if available; verify with a `GET` and compare the COUNT.
- The token itself was recoverable only because the owner pasted it — it is not
  in git, not in `.tg_token`, not in the workspace. Keep it that way.

## The owner's silence is durable — and how to READ the pinned blob

- ⭐ Owner said "أنا طفيت الإشعارات" (he turned alerts off from the panel
  himself). `/health` showed `alerts: off` + `confirm_only: on` at the same
  time — NOT a contradiction: `confirm_only` comes from the env (`DESK_CONFIRM_ONLY=1`),
  `alerts` from HIS panel choice. Two different sources, two different values.
- ⭐ **Proof his choice survives a restart: the pinned blob itself.**
  `getChat(933571066)` → `pinned_message.document` (`marketdesk-backup.json`)
  → `getFile` → download → `blob["settings"]` =
  `{"alerts": false, "confirm_only": true, ...}`, 72 trades. So the pinned copy
  already agrees with the live panel; nothing to repair.
- ⚠ **`DESK_ALERTS=1` had to be REMOVED from Render** after I set it: with the
  env guard, an env value beats the blob on every boot, so his "off" would have
  been undone by my own deploy. Panel choice must own silence.
- ⚠ **Telegram Bot API `getChat` rejects a JSON body** — `400 Bad Request:
  chat_id is empty`. It needs `application/x-www-form-urlencoded`
  (`urllib.parse.urlencode`). `getMe` worked with no body at all, which is what
  made the failure look like a bad chat id. (bot.py's `Telegram.call` already
  form-encodes; only my ad-hoc probe was wrong.)
- Read the token from Render's env API **into memory only**, never to a file,
  and `shred -u` anything transient. Repo verified clean of the token string.
